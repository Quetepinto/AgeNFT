Qué viaja al transferir el NFT

Un ageNFT es un cuerpo digital transferible. Una sola transacción onchain y el comprador hereda el paquete completo.

Viaja con el token ✅

  • Identidad — NFT + nombre + metadata onchain
  • Tesoro (TBA) — USDC, ETH y otros activos en la cuenta del token
  • Manifiesto — cerebro, memoria, chat, presupuesto (ageNFT/v1)
  • Memoria operativa — capa experiencial (según política de venta: full o reset); ver abajo
  • Personaje / canon — soul, URUIRU, skills (siempre)
  • Reflejos — límites de gasto definidos en manifiesto

Nunca viaja ❌

  • Vault 0 — passwords, API keys, manguera, tokens Telegram, credenciales runtime
  • PII del owner — notas privadas no exportadas; nunca en manifiesto onchain

Memoria experiencial — elección al vender

Conversaciones y hechos acumulados pueden transferirse completos o con reset. El comprador debe saberlo antes. URUIRU (personaje) siempre viaja; las vivencias, no necesariamente.

  • Con memoria — historial personal incluido (coleccionismo)
  • Solo capacidades — sin diario; puedes excluir skills concretas (ej. temas sensibles)
  • Cuerpo limpio — reset total experiencial; URUIRU sigue siendo URUIRU

Alquiler / prueba: terceros no ven datos personales (PII) ni Vault 0. Detalle: docs/research/memory-layers-access.md

Biblioteca — documentos de consulta

PDFs, corpus, plantillas y archivos que el agente abre para trabajar (RAG, OCR, etc.) son la Biblioteca — capa aparte del diario (M2) y las skills (M3).

  • Con el NFT (IPFS/toju) — solo si el vendedor los incluye en la oferta
  • Local o nube del owner — no viajan; en alquiler y trial el agente no puede leerlos
  • Prueba (trial) — lista explícita de docs incluidos; lo probado = lo comprado

Detalle: docs/research/library-storage-policy.md

Telegram al cambiar de owner

El bot (@Unit1_agent_bot) no viaja con el NFT. Es un cable en Vault 0 (token en el servidor), no parte del núcleo compacto del cuerpo.

  • Default: el comprador crea su bot en BotFather; el vendedor revoca el token y apaga su servicio.
  • Opcional: transferencia del mismo @handle vía BotFather — solo si ambos acuerdan.
  • Runtime: el motor debe comprobar ownerOf(tokenId) — si no coincide con la wallet del host, no contesta.

Decisión completa: docs/decisions/transfer-telegram-gateway.md

No viaja automáticamente ⚠️

  • Runtime / servidor — motor intercambiable (Hermes, OpenClaw, API mínima); infra del operador, no otro NFT
  • Memoria en disco local — hay que exportar a IPFS/toju antes del transfer
  • Claves del owner anterior — el nuevo dueño usa su wallet; re-firma x402
  • Telegram / gateways — reconfigurar credenciales; wizard post-transfer
  • Tier E (SaaS) — cuentas del vendedor; se desactivan → G/D por defecto

Mudanza fluida local → servicios default: transfer-local-hosting.md

Checklist post-transfer (MVP)

  1. Verificar owner del NFT en BaseScan
  2. Comprobar saldo USDC/ETH en la TBA
  3. Actualizar runtime con manifiesto unit-mainnet.json
  4. Probar un turno: npm run once:pay (payer TBA)
  5. Reconfigurar Telegram/Hermes si aplica
